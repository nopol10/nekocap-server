# Public subtitle API (proposal)

**Status:** proposal — not implemented.
**Audience:** NekoCap maintainers, and integrators building NewPipe-family
clients (Tubular, PipePipe, and other forks).

This document proposes two unauthenticated `GET` endpoints under the existing
`/api/v1` prefix that hand out NekoCap captions as ordinary **WebVTT** files at
stable HTTPS URLs, so a third-party player can offer NekoCap as an extra
subtitle source. The shape is driven by what NewPipe/ExoPlayer can actually
consume, but nothing in the API is NewPipe-specific.

---

## 1. How NewPipe pulls subtitles today

Verified against `TeamNewPipe/NewPipe@dev` and
`TeamNewPipe/NewPipeExtractor@dev`. NewPipe is still on **ExoPlayer 2.19.1**
(`gradle/libs.versions.toml`), not AndroidX Media3.

### 1.1 The model object

`extractor/src/main/java/org/schabi/newpipe/extractor/stream/SubtitlesStream.java`
carries a `MediaFormat`, a `Locale`, an `autoGenerated` flag and the raw language
code. Its constructor is private; the nested `Builder` requires `setContent(content, isUrl)`,
`setLanguageCode(...)` and `setAutoGenerated(...)`, and defaults `DeliveryMethod`
to `PROGRESSIVE_HTTP`. The constructor resolves the locale with:

```java
this.locale = LocaleCompat.forLanguageTag(languageCode).orElseThrow(
        () -> new ParsingException("not a valid locale language code: " + languageCode));
```

So **an invalid language tag throws** rather than skipping that one track.

### 1.2 Where tracks come from

`StreamExtractor.getSubtitlesDefault()` / `getSubtitles(MediaFormat)` are
non-abstract and return an empty list by default, so each service opts in.
`YoutubeStreamExtractor.getSubtitlesDefault()` delegates to
`getSubtitles(MediaFormat.TTML)`, reads `captions.playerCaptionsTracklistRenderer.captionTracks`
out of the player response, strips any existing `&fmt=` / `&tlang=` from each
`baseUrl` and appends `&fmt=<suffix>`.

`StreamInfo.extractOptionalData` then does
`streamInfo.setSubtitles(extractor.getSubtitlesDefault())` inside a try/catch
that only calls `streamInfo.addError(e)` — **a failing subtitle source degrades
gracefully and does not break the page**. `StreamInfo.setSubtitles(List<SubtitlesStream>)`
is public, which is the useful hook for an app-side injector.

### 1.3 How tracks reach the player

`app/src/main/java/org/schabi/newpipe/player/resolver/VideoPlaybackResolver.java`,
in `resolve(StreamInfo)`, filters the list through
`ListHelper.getUrlAndNonTorrentStreams(...)`, then for each stream with a
non-null `MediaFormat` builds a `MediaItem.SubtitleConfiguration` with
`Uri.parse(subtitle.getContent())`, `setMimeType(mediaFormat.getMimeType())`,
`setRoleFlags(...)` and `setLanguage(PlayerHelper.captionLanguageOf(context, subtitle))`,
creates a `SingleSampleMediaSource`, and merges everything into a
`MergingMediaSource`.

The captions popup in `VideoPlayerUi` (`buildCaptionMenu`, `onTextTracksChanged`)
is derived from **ExoPlayer's track list, not from `StreamInfo`** — so any
subtitle added before playback starts appears in the menu with zero UI changes.
Adding one mid-playback is not supported by the current architecture.

The fetch itself goes through `PlayerDataSource.getSingleSampleMediaSourceFactory()`,
which uses the `cacheDataSourceFactory` — subtitle URLs are fetched by ExoPlayer's
own HTTP stack and **cached on disk**.

### 1.4 The seven app files that touch `SubtitlesStream`

`VideoPlaybackResolver.java`, `PlayerHelper.java`, `StreamItemAdapter.java`,
`DownloadDialog.java`, `MissionRecoveryInfo.kt`, `DownloadMissionRecover.java`,
`StreamItemAdapterTest.kt`. There is **no plugin API and no third-party subtitle
source** anywhere in the codebase.

## 2. Requirements this imposes on the API

| # | Requirement | Why |
|---|---|---|
| R1 | Each track must be an **HTTPS URL**, not inline text | `ListHelper.getUrlAndNonTorrentStreams` drops `isUrl() == false`; `SingleSampleMediaSource` fetches the URL |
| R2 | Serve **WebVTT** as `Content-Type: text/vtt` | See 2.1 — SRT is unplayable in NewPipe |
| R3 | Send **`Content-Length`** | `StreamInfoWrapper.fetchMoreInfoForWrapper` probes size in the download dialog |
| R4 | Emit **valid BCP-47** language tags | `LocaleCompat.forLanguageTag(...).orElseThrow(...)` — one bad code kills the whole extraction |
| R5 | Provide something to **disambiguate same-language tracks** | `PlayerHelper.captionLanguageOf` labels by `Locale.getDisplayName()` alone |
| R6 | **Fail soft** — one cheap request, empty result rather than an error | The call sits inside a try/catch that only records the error |

### 2.1 Why not SRT

NewPipe's `MediaFormat` declares these subtitle entries:

| constant | suffix | mime | ExoPlayer 2.19.1 recognises? |
|---|---|---|---|
| `VTT` | `vtt` | `text/vtt` | yes (`MimeTypes.TEXT_VTT`) |
| `TTML` | `ttml` | `application/ttml+xml` | yes (`MimeTypes.APPLICATION_TTML`) |
| `SRT` | `srt` | `text/srt` | **no** — ExoPlayer wants `application/x-subrip` |
| `TRANSCRIPT1/2/3` | `srv1/2/3` | `text/xml` | **no** |

These mime strings are passed verbatim to ExoPlayer, so **only `VTT` and `TTML`
are playable**; `SRT` and `TRANSCRIPT*` exist only for the download path. WebVTT
is therefore the primary format. SRT is still offered because downloaders and
desktop players want it.

### 2.2 Two more behaviours to know

- **Live streams get no subtitles.** `resolve()` returns early via
  `PlaybackResolver.maybeBuildLiveMediaSource` before the subtitle block.
- **Label collision.** `captionLanguageOf` returns
  `getDisplayLanguageName()` plus an optional "(auto-generated)" suffix, and
  track selection matches on that string. Several NekoCap captions in one
  language — and NekoCap's "English" versus YouTube's own "English" — are
  indistinguishable in the menu. This is upstream issue
  [#7811](https://github.com/TeamNewPipe/NewPipe/issues/7811). Because this API
  returns *all* captions (see §3.1), a client that wants them distinguishable
  must make the small change in §9.2.

## 3. Proposed API

Base: `https://<api host>/api/v1`. Both routes are unauthenticated, consistent
with the existing `/api/v1` endpoints.

Unlike `search` and `captions/latest` — which mirror Parse cloud functions and
return a `{ "status": "success", ... }` envelope — this is a new third-party
contract, so **HTTP status codes are the contract** and there is no status
field. This divergence is deliberate; flag it in review if you would rather stay
consistent with the existing endpoints.

### 3.1 Discovery

```
GET /api/v1/subtitles?service=youtube&videoId=dQw4w9WgXcQ
```

Query parameters rather than path segments, for two reasons: NekoCap `videoId`s
are opaque per-platform strings that can contain `/`, `.` or `:` (archive.org,
TVer, bilibili multi-part ids), which are awkward to path-encode; and it leaves
room for a `url=` variant later without restructuring.

| param | required | default | notes |
|---|---|---|---|
| `service` | yes* | — | slug, case-insensitive (§7) |
| `videoSource` | yes* | — | numeric NekoCap `VideoSource`; alternative to `service`; `9999` folds to `0` |
| `videoId` | yes | — | max 256 chars |
| `format` | no | `vtt` | `vtt` \| `srt` — only affects `url` and `mimeType` in the response |
| `language` | no | — | comma-separated; accepts `en`, `en-US` or `en_US`; a base code expands to its sub-codes |
| `perLanguage` | no | `all` | `all` \| `best` — see below |
| `limit` | no | `50` | clamped to 1..100 |

\* exactly one of `service` / `videoSource`.

**`perLanguage` defaults to `all`**: every public caption is returned and the
client decides. `best` is offered for clients that would rather sidestep the
label-collision problem in §2.2 without patching their player. Either way the
list is returned in a defined **ranking order** so "first per language" is
meaningful: `verified` desc → `(likes - dislikes)` desc → `views` desc →
`updatedAt` desc → `id` asc as a deterministic tiebreak.

Captions are included only when all of the following hold: `rejected != true`,
`privacy ∈ {null, 0}` (Unlisted is creator-only, matching `canViewCaption`), the
language canonicalises to a valid BCP-47 tag (R4), and the caption actually has
cues (§4).

**Response `200`:**

```jsonc
{
  "video": {
    "service": "youtube",
    "videoSource": 0,
    "videoId": "dQw4w9WgXcQ",
    "title": "Example video"
  },
  "format": "vtt",
  "subtitles": [
    {
      "id": "AbCd123456",
      "language": "en-US",
      "languageName": "English (United States)",
      "sourceLanguage": "en_US",
      "format": "vtt",
      "mimeType": "text/vtt",
      "url": "https://api.nekocap.com/api/v1/subtitles/AbCd123456.vtt",
      "autoGenerated": false,
      "captionerId": "xxxxxxxxxx",
      "captionerName": "Someone",
      "verified": true,
      "likes": 12,
      "dislikes": 0,
      "views": 340,
      "translatedTitle": "Example video (translated)",
      "tags": [],
      "advanced": true,
      "stylingDropped": true,
      "updatedAt": 1712345678,
      "pageUrl": "https://nekocap.com/view/AbCd123456"
    }
  ]
}
```

Field notes:

- `language` is the BCP-47 tag, guaranteed to satisfy R4. `sourceLanguage` is
  NekoCap's raw code, for round-tripping back into other NekoCap APIs.
- `languageName` is best-effort via `Intl.DisplayNames`; clients on Android
  should prefer `Locale.forLanguageTag(language).getDisplayName()` so the label
  is localised to the user.
- `autoGenerated` is always `false` today — NekoCap captions are human-made. The
  field exists because NewPipe's builder requires it.
- `advanced` mirrors the existing `advanced` flag (the caption was uploaded as
  `.ass`/`.ssa`). `stylingDropped` says the served file cannot carry that
  styling — currently always equal to `advanced`, but kept separate so a future
  TTML or `.ass` passthrough can set them independently.
- `pageUrl` is the human-readable caption page, for attribution.

**A video with no captions is `200` with `"subtitles": []`, never an error** (R6).

**Errors** use HTTP status plus a small body:

```jsonc
{ "error": { "code": "unknown_service", "message": "…", "supportedServices": ["youtube", "…"] } }
```

| status | code |
|---|---|
| `400` | `missing_video_id`, `missing_service`, `unknown_service`, `unsupported_format`, `invalid_limit` |
| `429` | `rate_limited` (with `Retry-After`) |

### 3.2 Service list

```
GET /api/v1/subtitles/services
```

Returns the static slug → `VideoSource` table (§7) so integrators can discover
the mapping instead of hard-coding it. **Must be declared before the
`/subtitles/:file` route** — Express matches in registration order.

### 3.3 Content

```
GET  /api/v1/subtitles/{captionId}.vtt
GET  /api/v1/subtitles/{captionId}.srt
HEAD /api/v1/subtitles/{captionId}.vtt
```

Implement as a single `:file` param that the controller splits on the last `.`,
validating the id against `^[A-Za-z0-9]{6,24}$` and the extension against
`vtt|srt`; anything else is `404`. This avoids depending on how Express 5's
path-to-regexp v8 handles a literal `.vtt` suffix in a route pattern — see
§10.2.

Declare `@Head()` explicitly rather than relying on Express's HEAD→GET fallback,
so the download dialog's size probe is a tested part of the contract.

**Response headers:**

| header | value | why |
|---|---|---|
| `Content-Type` | `text/vtt; charset=utf-8` / `application/x-subrip; charset=utf-8` | R2; `text/srt` is not a real media type |
| `Content-Length` | `Buffer.byteLength(body, "utf8")`, set explicitly | R3 — must be the byte count, not `String.length` |
| `Cache-Control` | `public, max-age=600, stale-while-revalidate=86400, no-transform` | `no-transform` is what preserves `Content-Length`; see §8.1 |
| `ETag` | strong, from `_updated_at` + format + serializer version | conditional requests; the version component invalidates cached bodies when the serializer changes |
| `Access-Control-Allow-Origin` | `*` | cache-key independence for CDNs; overrides the reflected origin Nest's `enableCors({origin: true})` would send |
| `Vary` | `Accept-Encoding` | |
| `Content-Disposition` | `inline; filename="<id>.<ext>"` | downloader friendliness |
| `X-Robots-Tag` | `noindex` | |

`If-None-Match` hit → `304`, no body, no view increment.

`404` for an unknown id, and equally for a rejected, unlisted or cue-less
caption — the response must not reveal whether a private caption exists.

A caption that exists and passes the filters but flattens to zero cues after
sanitisation returns `200` with a header-only `WEBVTT\n\n` body rather than an
error, so a player already mid-load does not fail. Such captions are excluded
from discovery, so this is an edge path.

### 3.4 Examples

```sh
# discovery
curl -s 'https://api.nekocap.com/api/v1/subtitles?service=youtube&videoId=dQw4w9WgXcQ'

# only English captions, best one per language
curl -s 'https://api.nekocap.com/api/v1/subtitles?service=youtube&videoId=dQw4w9WgXcQ&language=en&perLanguage=best'

# the file itself, checking the Content-Length survives compression
curl -sI -H 'Accept-Encoding: gzip' 'https://api.nekocap.com/api/v1/subtitles/AbCd123456.vtt'
```

## 4. Caption source strategy: `content` is often empty

`captions.content` holds `JSON.stringify(CaptionDataContainer)` and is the
obvious input for a WebVTT serializer. **It is not reliably populated**, and the
gap lands on exactly the captions worth serving:

- `getCaptionContainersFromFile`
  (`nekocap/src/extension/background/feature/caption-editor/utils.ts`) sets
  `canAutoConvertToNekoCaption = false` for `.ass`/`.ssa` — the comment explains
  that "a large ass will freeze the page" — so `captionData` stays
  `{ tracks: [] }` unless the captioner manually ran the conversion in the
  editor.
- `updateCaption` (`src/cloud/main.ts`) sets
  `existingCaption.set("content", JSON.stringify({ tracks: [] }))` whenever a new
  raw caption is uploaded.

So a naive "serialize `content`" implementation would emit **empty files for
many advanced captions**. Two-tier answer:

1. **Primary:** serialize `content` when it contains cues.
2. **Fallback:** reconstruct cues from the raw `.ass` file.

The fallback needs no new dependencies. `index.js` configures no `filesAdapter`,
so Parse Server stores files in **GridFS in the same `DATABASE_URI`** — reachable
from the Nest layer's Mongoose connection without an HTTP round trip. (This
sidesteps the constraint noted in `loadCaption`, where cloud code cannot fetch
its own Parse file URL from inside Docker.) The client uploads
`compressToBase64(assText)`, and both `lz-string` and `ass-compiler` are already
runtime dependencies, so the chain is:

```
GridFS bytes → base64 → lz-string.decompressFromBase64 → ass-compiler.compile → cues
```

`ass-compiler` is already used server-side by `src/cloud/validator.ts`, and the
client's `convertAssCaptionsToNekoCaptionData` is a working reference for the
dialogue → cue mapping (layer → track, `\N` → newline, alignment, normalised
position).

**Before building the fallback, measure the blast radius**:

```js
db.captions.countDocuments({
  content: '{"tracks":[]}',
  rawContent: { $exists: true, $nin: [null, ""] },
});
```

If the count is small, shipping the primary path alone and excluding those
captions is defensible. If it is large — which the upload path above suggests —
the fallback is required for the API to be worth publishing. Either way it
should be a second phase: it needs an in-process cache, since decompressing and
compiling a large `.ass` per request is far more expensive than the primary path.

## 5. Serializer specification

Neither repo has a WebVTT writer. The client's `stringifyCaption`
(`nekocap/src/common/caption-parsers/index.ts`) implements SRT only and depends
on `subtitle` and `dompurify`, neither of which is a nekocap-server dependency —
and `src/nest/tsconfig.json` has no `@/*` alias, so the Nest layer cannot import
client code at all (§7). The serializer must be written locally with no new
dependencies.

### 5.1 Pipeline

1. **Parse.** `JSON.parse` in a try/catch; anything that is not an object with a
   `tracks` array becomes `{ tracks: [] }`. Never throw on stored data.
2. **Flatten.** `tracks.flatMap(t => t.cues ?? [])`, decorated with the original
   index and sorted by `(start, index)` so ties preserve track order. This
   mirrors the client's `flattenNekoCaption`.
3. **Normalise each cue.**
   - `start`/`end` must be finite (accept numeric strings via `Number()`);
     otherwise drop the cue.
   - `start = Math.max(0, Math.floor(start))`, `end = Math.floor(end)`.
   - If `end <= start`, set `end = start + 1` — deterministic and still valid,
     rather than fabricating a duration.
   - Sanitise the text; drop the cue if nothing survives.
   - Keep overlapping cues; both formats allow them and ExoPlayer handles them.
4. **Emit.**

### 5.2 Sanitiser (no dompurify)

A character scanner, not a chain of regex replacements:

- Normalise `\r\n` and `\r` to `\n`; strip control characters
  (` -`, ``, ``, `-`) and any BOM;
  right-trim each line; collapse runs of newlines to one. **Collapsing blank
  lines is a correctness requirement, not cosmetics** — a blank line terminates
  a cue in both WebVTT and SRT.
- Tokenise: on `<`, look ahead for exactly `</?[bui]>` (case-insensitive, no
  attributes, no internal whitespace). A match becomes a tag token; anything
  else — `<script…`, `<font color=…>`, a stray `<` — is literal text.
- Balance: maintain a stack of open tags, drop unmatched closers, auto-close
  anything still open at the end of the cue.
- Render text runs per format:
  - **VTT:** escape `&` → `&amp;`, then `<` → `&lt;`, then `>` → `&gt;`.
    Allowed tags are emitted literally. Because every `>` in text becomes
    `&gt;`, a literal `-->` inside a cue is structurally impossible — no special
    case needed.
  - **SRT:** SRT is not markup, so entity escaping would display literally.
    Delete `<` and `>` from text runs and leave `&` alone. Deleting `>` also
    neutralises `-->`.
- Optionally wrap right-to-left text in `‫…‬` after stripping existing
  marks, mirroring the client's behaviour in `stringifyNekoToSrt`.

### 5.3 Timestamps

`floor(ms/3600000)` hours, then minutes, seconds, milliseconds; zero-padded to
at least two digits for hours but never truncated past 99h. WebVTT uses `.`
before the milliseconds, SRT uses `,`. Always emit the hours field — both
parsers accept it and uniformity simplifies testing.

### 5.4 Output

```
WEBVTT

NOTE
Caption by <captionerName> — https://nekocap.com/view/<id>
Provided by NekoCap. Styling may be simplified.

1
00:00:01.000 --> 00:00:04.000
Hello &amp; <b>welcome</b>
```

The header stays a bare `WEBVTT` for maximum parser tolerance; attribution goes
in a `NOTE` block, which ExoPlayer's `WebvttDecoder` skips. Numeric cue
identifiers are emitted for both formats.

Cue settings may be derived from `layout` behind an option, in its own pure
function: alignment 1/4/7 → `align:start`, 3/6/9 → `align:end`, 7-9 →
`line:0%`, 4-6 → `line:50%`; an explicit `layout.position` maps to
`position:{x*100}% line:{y*100}%`. Emit only non-default values. SRT ignores
layout entirely and has no comment syntax, so it gets no attribution block —
attribution for SRT lives in the discovery JSON and the response headers.

### 5.5 Cases the tests must cover

`content` missing, `""`, `"null"`, or malformed JSON; `{"tracks":[]}`; tracks
with `cues: null`; a single cue at `t=0`; `start > 24h`; NaN, Infinity, negative
and string times; `end <= start`; overlapping cues; whitespace-only text; text
containing `-->`, a pre-existing `&amp;`, `<script>`, an unbalanced `<b>`,
nested `<b><i>`, `\r\n`, a double newline, and NUL; and emoji/CJK text with
byte-length assertions so `Content-Length` correctness is pinned.

## 6. Language tags

NekoCap stores codes with underscores (`en_US`); R4 needs hyphens.

`toBcp47(code)`: trim → `_`→`-` → collapse doubled separators →
`Intl.getCanonicalLocales(tag)[0]`. On `RangeError`, retry with the primary
subtag alone; if that also fails, return `undefined` and **drop the caption from
discovery** — emitting it would throw inside `SubtitlesStream`'s constructor and
take down the entire extraction (R4).

Note that `Intl.getCanonicalLocales` validates *syntax*, not existence: `unk`
passes. Reject codes whose primary subtag is not 2–3 alphabetic characters as a
cheap extra guard.

Empirically this path costs nothing: all **512** language keys in
`nekocap/src/common/languages.ts` canonicalise cleanly under
`Intl.getCanonicalLocales(k.replace(/_/g, "-"))` — 512 accepted, 0 rewritten, 0
thrown. `submitCaption` only truncates the code to 20 characters and never
validates it, so the drop rule is a guard against junk, not a common path.

For the `language=` query filter, invert the transform (`-`→`_`) and reuse the
base-expansion regex `^en($|_.*)` that `SearchService.captionLanguageMatch`
already uses, so `language=en` matches `en`, `en_US` and `en_GB`.

`languageName` uses `Intl.DisplayNames` inside a try/catch, falling back to the
tag itself for small-ICU Node builds.

## 7. Video source mapping

NewPipe's `ServiceList` is YouTube 0, SoundCloud 1, MediaCCC 2, PeerTube 3,
Bandcamp 4. NekoCap's `VideoSource` is a different, explicitly-numbered enum of
22 sources plus the in-website pseudo-source `NekoCapYoutube = 9999`. **Only
YouTube overlaps**, and the fact that both call it `0` is a coincidence, not a
contract — which is why slugs are the primary key and `videoSource` is only an
alias for callers that already store NekoCap's enum.

| slug | `VideoSource` | | slug | `VideoSource` |
|---|---|---|---|---|
| `youtube` | 0 | | `nogidoga` | 12 |
| `tver` | 1 | | `abema` | 13 |
| `vimeo` | 2 | | `dailymotion` | 14 |
| `niconico` | 3 | | `bilibili-tv` | 15 |
| `bilibili` | 4 | | `archive-org` | 16 |
| `bilibili-bangumi` | 5 | | `tbs-free` | 17 |
| `netflix` | 6 | | `instagram` | 18 |
| `amazon-prime` | 7 | | `unext` | 19 |
| `twitter` (alias `x`) | 8 | | `lemino` | 20 |
| `wetv` | 9 | | `oned` | 21 |
| `tiktok` | 10 | | | |
| `iqiyi` | 11 | | | |

`9999` folds to `0`, mirroring `WebSourceToVideoSourceMap`. The resolver returns
the **stringified** number, because `captions.videoSource` and `videos.source`
are stored as strings in Mongo even though the Nest `Video` schema declares
`source?: number`. This string/number mismatch is the main footgun in any new
query path.

PeerTube is multi-instance, so `(serviceId, id)` is not globally unique there —
if PeerTube support is ever added, the key has to include the instance.

Because `src/nest/tsconfig.json` has no `@/*` path alias, this table must be
**duplicated** inside `src/nest/`, following the existing convention of a
`// Mirrors X in nekocap's …` comment (as `search.service.ts` and the shared
schemas already do). A test should assert the table length equals
`TOTAL_SUPPORTED_SITES` in `src/nest/constants.ts` so the two cannot drift
silently.

## 8. Operational concerns

This endpoint would be hit on essentially every video open by a large userbase,
so the operational shape matters as much as the payload.

### 8.1 `compression()` versus `Content-Length` (R3)

`index.js` mounts `app.use(compression())` globally, and gzipping removes
`Content-Length`. It does **not** need changing: `compression@1.8.1` skips any
response carrying `Cache-Control: no-transform`, and never compresses `HEAD`.
Including `no-transform` in the content route's `Cache-Control` therefore
satisfies R3 without touching global middleware.

This must be verified against a running server with a real request — a unit test
cannot observe middleware that lives outside Nest:

```sh
curl -sI -H 'Accept-Encoding: gzip' 'https://…/api/v1/subtitles/<id>.vtt' | grep -i 'content-length\|content-encoding'
```

Discovery responses keep compression on: JSON compresses well and has no
`Content-Length` requirement.

### 8.2 Caching

Discovery: `public, max-age=300, stale-while-revalidate=3600` plus an ETag over
the serialised payload. Content: as in §3.3. Captions are editable, so no
`immutable`. Both are safely CDN-cacheable because `Access-Control-Allow-Origin`
is a constant `*` rather than a reflected origin.

Nest's `enableCors({ origin: true })` adds `Vary: Origin`, which slightly
fragments CDN cache keys even though the header value is forced to `*`.
Acceptable, but worth knowing.

`helmet()` sets `X-Content-Type-Options: nosniff`, so the `Content-Type` has to
be exactly right or browsers will refuse the response. The tests cover it.

### 8.3 Indexes

None needed. Discovery hits the existing `captions.videoId_1_videoSource_1`; the
captioner join hits `captioner.userId_1`; the title lookup hits the
`videos.sourceId_1_source_1_language_1` prefix; content lookups hit `_id_`
(Parse object ids are 10-character **strings**, so no `ObjectId` casting).

If profiling later shows the residual `rejected` / `privacy` filtering is hot, a
`{videoId: 1, videoSource: 1, rejected: 1, privacy: 1}` index would help — and
it must also be added to `database/nekocap-schema.json` under
`_metadata.indexes`, since that file is the documented import artifact and the
Nest layer must not own Parse's schema.

Do **not** reuse `CAPTION_DETAILS_JOIN_PIPELINE` from
`src/nest/captions/captions.service.ts` wholesale: its `videos` `$lookup`
matches on `sourceId` only and ignores `source`, so a same-id video on a
different service can attach the wrong title. Discovery already knows both keys
and only needs the `captioner` join.

### 8.4 Rate limiting

There is currently **none anywhere in the repo**, and no reverse proxy in this
deployment — `index.js` terminates TLS itself. Options:

- A small zero-dependency guard scoped to this controller (fixed window, bounded
  `Map` with periodic sweep, keyed by `req.ip`), configured by env with a
  disable switch. Preferred: it avoids adding a runtime dependency to a
  webpack-bundled server for one controller.
- `@nestjs/throttler` — a new dependency, worth it once a second consumer exists.

Either way, note that `index.js` never calls `app.set("trust proxy", …)`, so if
the deployment is ever fronted by a proxy, `req.ip` is the proxy's address and
IP-based limiting collapses to a single bucket. In-process limiting also resets
on every deploy; real protection needs a CDN or proxy in front.

### 8.5 View counting

Increment on the **content** route only — discovery fires on every video open
and would inflate every caption on a popular video. Fire-and-forget
`updateOne({_id}, {$inc: {views: 1}})`, skipped for `HEAD` and `304`, errors
swallowed, gated by an env flag.

Two properties worth noting. A direct `$inc` does **not** bump `_updated_at`, so
it will not churn ETags — unlike Parse's `caption.increment("views"); caption.save()`
in `loadCaption`. And caching means systematic undercounting, which is
acceptable for a metric that already only approximates readership.

Worth deciding with the maintainer: whether API traffic should land in `views`
at all, or in a separate `apiViews` field so it does not distort the existing
number.

### 8.6 Absolute URLs

The response must contain absolute HTTPS URLs (R1), and they cannot be derived
from the request because `trust proxy` is unset. Introduce a config value (e.g.
`PUBLIC_API_BASE_URL`), falling back to `PUBLIC_SERVER_URL` with a trailing
`/parse` stripped, and to `http://localhost:${PORT}` in development. Fail loudly
at bootstrap in production if the resolved base is not `https://`.

`pageUrl` needs the website origin, which the server does not currently have —
the frontend's `NEXT_PUBLIC_WEBSITE_URL` has no server-side counterpart. Add one,
or omit `pageUrl` when it is unset.

### 8.7 Observability

`Sentry.Handlers.errorHandler()` is registered **after** the Nest bootstrap in
`index.js`, and Nest's own `ExceptionsHandler` responds first, so Express error
middleware never runs for `/api/v1`. Nothing in the Nest layer currently reaches
Sentry. Add an explicit `Sentry.captureException` or a module-scoped Nest
exception filter — otherwise a broken discovery endpoint is indistinguishable
from "this video has no captions", because R6 requires it to fail soft.

### 8.8 Attribution and moderation

Captions are user-submitted, so attribution should be carried in three places:
`captionerName` and `pageUrl` in the discovery JSON, the `NOTE` block in the VTT
body, and this document's usage guidance. `X-NekoCap-Caption-Id` and
`X-NekoCap-Captioner` response headers make downstream logging easy. Rejected and
unlisted captions are excluded everywhere, so the existing moderation flow
(`rejectCaption`, `privacy`) governs this API for free.

Clients should label these tracks as community-contributed rather than presenting
them as the platform's own.

## 9. Integrating from a NewPipe fork

### 9.1 Where to inject

The recommended point is **app-side**, in
`app/src/main/java/org/schabi/newpipe/util/ExtractorHelper.java`:

```java
public static Single<StreamInfo> getStreamInfo(final int serviceId, final String url,
                                               final boolean forceLoad) {
```

Map the resulting `StreamInfo` through a helper that fetches the discovery
endpoint, converts each entry to a `SubtitlesStream`, and calls
`info.setSubtitles(merged)` (the setter is public). Because `ExtractorHelper`
stores the result in `InfoCache`, this costs one lookup per video rather than
one per playback, and `StreamInfo` / `SubtitlesStream` are `Serializable` so
`@State` saving still works.

Building each track:

```java
new SubtitlesStream.Builder()
        .setContent(track.url, true)          // R1 — must be a URL
        .setMediaFormat(MediaFormat.VTT)      // R2 — VTT or TTML only
        .setLanguageCode(track.language)      // R4 — BCP-47 or this throws
        .setAutoGenerated(false)
        .setId("nekocap-" + track.id)
        .build();
```

Wrap the fetch so a failure yields the unmodified `StreamInfo` (R6), and put it
behind an opt-in setting that is off by default.

**Alternative, not recommended:** appending inside
`YoutubeStreamExtractor.getSubtitles(MediaFormat)` is a smaller diff but puts a
third-party network call inside the extractor library, which has to go through
the `Downloader` abstraction and couples a service-specific extractor to an
unrelated service. Keep the extractor clean.

**Not viable:** adding sources in `VideoPlaybackResolver.resolve()` — that runs
on the playback path, where a blocking network call is unacceptable, so the URLs
would have to be pre-resolved anyway.

### 9.2 Making same-language tracks distinguishable

Because discovery returns every caption (§3.1), a fork should also touch
`PlayerHelper.captionLanguageOf(Context, SubtitlesStream)` — the single method
that decides the captions-menu label. Keying off the `"nekocap-"` id prefix set
above, append the source (and optionally the captioner name) to the display
name. Without this, multiple NekoCap tracks and YouTube's own track all read
"English" and are indistinguishable, which is upstream issue #7811.

Alternatively, request `perLanguage=best` and accept one NekoCap track per
language; it still collides with the platform's own track of the same language,
but the menu stays readable with no code change.

Note also that `captionLanguageStemOf` strips a parenthesised suffix, and that
track selection matches on the display string — so whatever label scheme you
pick must round-trip through `setPreferredTextLanguages`.

### 9.3 Why forks rather than upstream

`.github/CONTRIBUTING.md` opens with an explicit feature freeze — "Please do
**not** open pull requests for *new features* now, as we are planning to rewrite
large chunks of the code" (see issue
[#10003](https://github.com/TeamNewPipe/NewPipe/issues/10003)) — and the
[maintainers' guide](https://teamnewpipe.github.io/documentation/09_maintainers_view/)
asks contributors to "avoid introducing niche features to satisfy a small
handful of users". The closest existing request, issue
[#2902](https://github.com/TeamNewPipe/NewPipe/issues/2902) ("custom subtitles
support"), has carried the `niche` label since 2019 with no maintainer
engagement.

The precedent for optional third-party services is negative: SponsorBlock has
been requested at least six times and closed every time; Return YouTube Dislike
likewise. Both live in forks (Tubular, PipePipe). Upstream NewPipe contacts no
external hosts beyond its own update check and user-initiated crash reports.

This API does satisfy F-Droid's inclusion policy, which `CONTRIBUTING.md`
requires — it is a plain REST endpoint with no proprietary SDK and no binary
blobs — so the obstacle is product policy, not licensing. NekoCap's server is
MIT-licensed and the client is GPL-3.0, both compatible with NewPipe's
GPL-3.0-or-later.

Note too that `CONTRIBUTING.md` restricts the use of generative AI for new
features and larger code changes; a human-authored integration is expected.

## 10. Implementation sketch

Nothing here is built yet. If the design is accepted, the shape that fits the
existing Parse → NestJS migration (`b1d4b78`, `e1b5d54`, `453bb86`) is:

### 10.1 Files

**Pure, no DB, fully unit-testable:**

- `src/nest/shared/subtitle-format/types.ts` — local mirrors of
  `CaptionDataContainer`, `Track`, `NekoCaption`, `CaptionAlignment`.
- `src/nest/shared/subtitle-format/timestamps.ts`
- `src/nest/shared/subtitle-format/markup.ts` — tokeniser, balancer, per-format
  sanitisers, RTL wrap.
- `src/nest/shared/subtitle-format/serializer.ts` — parse, flatten, serialise,
  `SERIALIZER_VERSION`, cue settings from layout.
- `src/nest/subtitles/language-tags.ts` (§6)
- `src/nest/subtitles/video-sources.ts` (§7)

Placing the serializer under `shared/` rather than `subtitles/` keeps it
available to a future "export caption" endpoint.

**Module wiring:**

- `src/nest/shared/schemas/caption.schema.ts` — add `content?: string` as a
  `@Prop`. The schema is `strict: false` so reads already work, but the typed
  prop should exist.
- `src/nest/shared/schemas/captioner.schema.ts` — move from
  `src/nest/captions/schemas/`, following the precedent of commit `5e87f0b`
  which moved the caption schema, so both modules share one definition.
- `src/nest/subtitles/{constants,types,subtitles.service,subtitles.controller,subtitles.module}.ts`
- `src/nest/app.module.ts` — register `SubtitlesModule`.

**Phase 2, only after measuring §4:**
`src/nest/subtitles/ass-fallback.service.ts` — GridFS read → `lz-string` →
`ass-compiler` → cues, with an in-process LRU.

No webpack, tsconfig or dependency changes are required — everything under
`src/nest` is compiled by the existing ts-loader rule with `transpileOnly: false`,
so `npm run build` type-checks the new code.

### 10.2 Route registration caveat

There are **three** copies of `path-to-regexp` in the dependency tree — `8.4.2`
at the root (used by Express 5.2.1, the app Nest attaches to via
`ExpressAdapter`), `0.1.13` under `@nestjs/platform-express`'s own Express 4, and
`3.3.0` under `@nestjs/core`. Which one ends up parsing a route pattern
containing a literal `.vtt` suffix is not settleable by inspection, and the three
versions disagree about how a parameter binds against a following dot.

The single-`:file`-param design in §3.3 sidesteps the question entirely and is
provably safe under any of them. If you do prefer a literal suffix in the route,
verify it against a running server rather than a unit test.

Registration order matters: `/subtitles/services` must be declared before
`/subtitles/:file`.

### 10.3 Tests

`@nestjs/testing`, `supertest` and `@nestjs/throttler` are **not** installed, so
tests stay service-level, as `test/nest/search.test.ts` already does (direct
service instantiation via `connection.model(...)`, `MongoMemoryReplSet`, graceful
skip when no `mongod` binary is available).

- `test/nest/subtitle-serializer.test.ts` — the full case list in §5.5, golden
  strings for a small caption in both formats, byte-length assertions for
  CJK/emoji.
- `test/nest/language-tags.test.ts` — `en_US`→`en-US`, `zh_Hans_CN`,
  `yue_Hant_HK`, base fallback, junk → `undefined`, filter round-trip, plus a
  table-driven sweep over a sample of real codes.
- `test/nest/video-sources.test.ts` — slug/alias/number resolution,
  case-insensitivity, `9999`→`"0"`, unknown → error, and length ===
  `TOTAL_SUPPORTED_SITES`.
- `test/nest/subtitles.test.ts` — in-memory Mongo, documents seeded in Parse's
  on-disk shape (`videoSource` as a string, `_updated_at`, `content` as a JSON
  string): rejected and unlisted excluded; `{"tracks":[]}` excluded; ranking
  including every tiebreak level; `perLanguage=best`; `language=` base
  expansion; unparseable language dropped; URLs absolute and `https`; unknown id
  → not found; view `$inc` observed for `GET` and not for `HEAD`/`304`.
- Controller tests with a stub `res` recording `setHeader`/`status`/`send`:
  exact `Content-Length` for multibyte bodies, `Cache-Control` contains
  `no-transform`, `ETag` + `If-None-Match` → `304`, `ACAO: *`, `.srt` mime, bad
  extension → `404`, `/services` not swallowed by `:file`.

Beyond tests: `npm run build` as the type-check gate, the `curl` check in §8.1,
a conditional-request check, and a real playback smoke test by loading the URL in
ExoPlayer or VLC. On the client side, confirm the track appears in the captions
menu and that the download dialog shows a size.

## 11. Open questions and risks

1. **ASS coverage (§4)** is the biggest open question. Measure the affected
   population before committing to a phasing — if most advanced captions have an
   empty `content`, the GridFS fallback is not optional.
2. **Styling is lost either way.** Even with the fallback, WebVTT cannot carry
   ASS positioning, karaoke or font effects. `stylingDropped` tells clients so.
   A future `.ass` passthrough or TTML output could narrow the gap; NewPipe's
   `MediaFormat` has no ASS entry, so it would only help other consumers.
3. **Label collision (§2.2)** is a genuine UX problem that the server cannot
   solve alone, given the decision to return all captions.
4. **Contract drift** between the duplicated source/language tables and the
   client is inherent to the tsconfig split. The `TOTAL_SUPPORTED_SITES` test
   and the mirror comments reduce it but do not eliminate it.
5. **Scraping.** The content route is trivially enumerable and in-process rate
   limiting resets on deploy. Anything serious needs a CDN or proxy.
6. **`compression` behaviour (§8.1)** depends on `no-transform` handling in
   `compression@1.8.x`; pin it with a real request, and re-check on upgrade.
7. **Silent failure (§8.7).** Without explicit Sentry capture, a broken endpoint
   looks exactly like a video with no captions.
8. **Upstream adoption (§9.3)** is unlikely in the current freeze. The API is
   worth having regardless — it is generic, and any player, script or archival
   tool can use it — but the NewPipe-shaped payoff depends on forks.
